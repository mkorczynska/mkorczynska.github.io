GIT i GitHub - wprowadzenie

Czym jest git?

Git to rozproszony system kontroli wersji (🇬🇧VCS – Version Control System). Służy do śledzenia zmian w plikach, umożliwia pracę zespołową, cofanie zmian, tworzenie alternatywnych wersji projektu oraz bezpieczne eksperymentowanie.

  • działa lokalnie – bez internetu,
  • umożliwia cofanie zmian,
  • wspiera pracę zespołową,
  • pozwala tworzyć alternatywne wersje projektu.

Rozproszony oznacza, że nie istnieje jedno główne repozytorium, z którym łączą się współpracownicy. Każdy posiada na swoim komputerze kopię całego repozytorium. Zaletą takiego podejścia jest możliwość pracy offline.

GitHub

GitHub to hostingowy serwis internetowy, w ramach którego wykorzystywanu jest system kontroli wersji (git).

Interfejs GitHub jest stosunkowo prosty, co sprawia, że korzystać z niego mogą osoby nieznające gita.

GitHub nie służy jedynie do hostowania projektów programistycznych - może się okazać przydatny nawet podczas pisania dłuższych publikacji.

Zaletą serwisu GitHub jest możliwość korzystania z niego za darmo

Jak rozpocząć pracę z GitHub

Podstawowe pojęcia

Zrozumienie działania systemu kontroli wersji wymaga poznania kilku kluczowych pojęć.

Repozytorium

Katalog projektu wraz z ukrytą strukturą .git, w której Git przechowuje całą historię zmian (commity, gałęzie, tagi).

Rodzaje repozytoriów:

  • lokalne
  • zdalne

Commit

Zapis aktualnego stanu projektu w historii repozytorium. Zawiera informacje o autorze, dacie, opisie zmian oraz wskaźnik do poprzedniego commita. Commit nie zapisuje pojedynczego pliku, lecz cały stan projektu w danym momencie - jeżeli pewne pliki się nie zmieniły, git przechowuje tylko łącze do ich poprzednich wersji. Każdy commit ma swój unikatowy identyfikator (SHA1).

Working tree

Working area/working directory (katalog roboczy, kopia robocza) to pliki, które użytkownik edytuje, obszar, w którym dokonuje zmian - znajdują się tutaj wszystkie zmiany (nie zcomiitowane i nieznajdujące się w staging area). W najprostszym ujęciu, to wszystko to, co pojawi się po zastosowaniu polecenia ls w folderze repozytorium (lokalne pliki projektu).

Staging area

Index to przestrzeń pośrednia pomiędzy working area a repozytorium. Trafiają tu zmiany dodane poleceniem git add. Tylko pliki znajdujące się w staging area zostaną zapisane w commicie - polecenie git commit stworzy commit na podstawie plików w tym obszarze.

Branch

Gałąź to niezależna linia rozwoju projektu. Pozwala pracować nad nową funkcjonalnością bez wpływu na główną wersję projektu. Domyślną gałęzią jest zazwyczaj main. Każda gałąź to oddzielny katalog roboczy i staging area. Jeżeli praca w ramach gałęzi zostanie ukończona, możliwe jest scalenie jej z główną częścią projektu.

Merge

Scalanie to operacja pozwalająca na połączenie ze sobą gałęzi (branch).

Remote

Zdalne repozytoria git, najczęściej umieszczone na serwisach takich jak GitHub lub GitLab. Umożliwiają współpracę zespołową oraz synchronizację zmian pomiędzy różnymi komputerami.

Tagowanie

Polega na oznaczaniu konkretnych commitów etykietami (tagami), np. wersjami v1.0 lub release-2025. Tagi są najczęściej używane do oznaczania stabilnych wydań projektu.

Aliasy

Skrócone nazwy poleceń git definiowane przez użytkownika. Pozwalają uprościć i przyspieszyć pracę, np. alias git st zamiast git status.

HEAD

Wskaźnik pokazujący, na którym commicie aktualnie pracuje użytkownik. Zwykle wskazuje na ostatni commit bieżącej gałęzi. Zmienia się z każdym nowym commitem lub podczas przejścia na inny commit poprzez zmianę gałęzi (branch).

Instalacja GIT

Proces instalacji git jest stosunkowo łatwy niezależnie od systemu operacyjnego.

Windows

Pobierz Git for Windows ze strony git-scm.com i zainstaluj. Po instalacji używaj Git Bash.

git --version

Linux (Ubuntu / Debian) 

sudo apt update
sudo apt install git

macOS

brew install git

Konfiguracja

Tworzenie repozytorium 

git init

Polecenie inicjalizuje nowe repozytorium w bieżącym katalogu.

Sprawdzenie statusu

git status

Pokazuje: zmodyfikowane pliki, pliki gotowe do commita, pliki nieśledzone.

Wyświetlanie zatwierdzonych migawek

git log

Pokazuje historię commitów

Można używać flag

  • -n <limit> - ograniczenie liczby wyświetlanych commitów
  • --oneline - commit w jednym wierszu
  • -p - pełny wykaz różnic
  • --author="<pattern>" - szukanie commitów konkretnego autora
  • --grep="<pattern>" - szukanie według wzorca
  • <since>..<until> - commity z określonego przedziału
  • <file> - commity zawierające konkretny plik
  • --graph - wykres commitów (tekstowy)
  • --decorate - dodawanie nazw gałęzi lub tagi

Polecenie git-config

Polecenie git config pozwala na ustawienie opcji konfiguracyjnych takich jak np. nazwa użytkownika czy adres email

Opcje konfiguracyjne przechowywane są w trzech plikach - różnią się one zakresem obowiązywania

  • local <repo> /.git/config - domyślny zakres działania polecenia git config (jeśli nie została podana flaga, domyślnie jest --local). Ustawienia obowiązują dla repozytorium.
  • global /.gitconfig - poziom globalny odnosi się do konkretnego użytkownika systemu operacyjnego (flaga --global)
  • system $(prefix) - poziom systemu obejmuje cały komputer i dotyczy wszystkich jego użytkowników

Kolejność: local-->global-->system

Konfiguracja nazwy użytkownika oraz adresu email

git config --global user.name "Jan Kowalski"
git config --global user.email "jan@example.com"

Konfiguracja ta jest zapisywana globalnie i używana we wszystkich repozytoriach.

Określa ona nazwę autora oraz adres mailowy dla wszystkich commitów w bieżącym repozytorium.

Flaga --global powoduje, że ustawienia zostaną zastosowane dla bieżącego użytkownika.

Konfiguracja edytora

git config --system core.editor <editor>

Powyższe polecenie umożliwia ustawienie edytora tekstu dla wszystkich użytkowników urządzenia (flaga --system)

W polu <editor> należy podać nazwę edytora np. vim, atom, emacs, nano.

Kolorowanie danych wyjściowych

Git umożliwia korzystanie z kolorowania składni danych wyjściowych

git config --global color.ui false

Powyższe polecenie wyłączy kolorowanie składni. Domyślnie color.ui ustawione jest na auto.

Można zastosować szczegółowe ustawienia kolorów dla konkretnych poleceń

Wartości kolorów

Istnieje wiele szczegółowych ustawień kolorów, które można ustawiać na false, auto lub always.

Przykładowe obsługiwane kolory:

  • czarny
  • czerwony
  • zielony
  • żółty
  • niebieski

Istnieje również możliwość oznaczania kolorów wartościami szesnastkowymi np. #efefef.

color.branch - konfiguracja koloru wyjściowego dla polecenia git branch
color.diff - konfiguracja koloru wyjściowego dla poleceń git diff, git log, git show

Aliasy

Alias można rozumieć jako skrót. Używany jest, by zastąpić długie polecenia krótszymi, dzięki czemu wprowadzanie ich staje się szybsze.

Zamiast wpisywać całe polecenie np. git checkout można użyc aliasu git co

Aliasy tworzy się za pomocą polecenia git config - nie istnieje polecenie alias

git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.ci commit
git config --global alias.st status

Powyzsze polecenia ustawią odpowiednie aliasy (skroty) dla poleceń git checkout, git branch, git commit, git status

Ustawienie flagi --global powoduje, że aliasy będą dostępne dla wszystkich.

Ustawienie aliasu nie sprawia, że standardowe polecenia przestają być dostępne - nadal możliwe jest korzystanie z pełnych wersji poleceń.

Aliasy mają takie samo znaczenie jak pełne polecenia.

Zapisywanie zmian

Zapisywanie zmian w git nie jest tożsame z zapisywaniem zmian np. w dokumencie tekstowym. W tym przypadku ma ono charakter zatwierdzania.

Podstawą pracy z git jest stosowanie poleceń git add oraz git commit.

Uzytkownik wprowadza zmiany w projekcie, następnie zapisuje je w przechowalni korzystając z polecenia git add, a na koniec zatwierdza używając polecenia git commit.

Dodawanie plików do przechowalni

Przechowalnia to stan przejściowy między katalogiem roboczym a historią projektu.

git add plik.txt

Powyższe polecenie spowoduje, że do przechowalni zostanie dodany plik.txt

Opcje polecenia git add

<file> - zapisanie w przechowalni zmian w pliku

<file> - zapisanie w przechowalni zmian w folderze

-p - uruchomienie interaktywnej sesji zapisu umozliwiającej wybranie fragmentów pliku do dodania do przechowalni (y, aby zapisać fragment w przechowalni; n, aby zignorować fragment; s, aby podzielić go na mniejsze fragmenty; e, aby ręcznie wyedytować; albo q, aby wyjść)

Commit zapisuje aktualny stan plików w historii projektu.

Zatwierdzanie zmian

Korzystanie z systemu kontroli wersji przypomina śledzenie osi czasu reprezentującej postępy w projekcie

Commit w tym kontekście można uznać za migawkę stanu projektu w danym momencie. Commit zapisuje całą zawartość pliku za każdym razem, gdy powstaje.

git commit

Powyższe polecenie spowoduje, że migawka elementów znajdujących się w przechowalni zostanie zatwierdzona i uruchomiony zostanie monit z prośbą o wprowadzenie wiadomości zatwierdzenia (wiadomość commitowa) - konieczne jest zapisanie pliku i zamknięcie edytora, by utworzyć commit.

Opcje polecenia git commit

-a - zatwierdza migawkę wszystkich zmian w katalogu roboczym i dotyczy to plików, które na jakimś etapie zostały dodane do przechowalni za pomocą polecenia git add

-m "message" - polecenie tworzące commit z podanym w cudzysłowie komunikatem zatwierdzenia (wiadomością commitową)

-am - połączenie opcji -a i -m

-amend - edycja ostatniego commitu (nie jest to tworzenie nowego commitu); wykorzystanie tej opcji uruchamia edytor tekstu z prośbą o zmianę poprzedniej wiadomości commitowej

Przykład

git add hello.py
git status
On branch main
Changes to be committed:
(use "git reset HEAD <file>..." to unstage)
new file: hello.py

Wykaz różnic

W ramach git istnieje funkcja umożliwiająca pobranie dwóch zestawów danych i wskazanie różnic pomiędzy nimi. Porównywanymi danymi mogą być commity, gałęzie, pliki.

Aby skorzystać z tej funkcji należy użyć polecenia git diff. Domyślnie to polecenie wskazuje wszystkie niezatwierdzone od ostatniego commitu zmiany.

diff --git a/index.html b/index.html
index 00936d4..ab0b923 100644
--- a/index.html
+++ b/index.html
@@ -114,8 +114,8 @@

Wynik polecenia git diff składa się z danych wyjściowych porównania, metadanych, znaczników zmian oraz elementów wykazu. Dane wyjściowe informują, co zostało porównane. Znaczniki zmian to legenda opisująca oznaczenia zmian w obu porównywanych źródłach - w tym przypadku "---" odnosi się do pliku a/index.html, a "+++" do pliku b/index.html. Ostatnia część to lista zmian będąca faktycznym wykazem różnic. Nie są wyświetlane całe pliki, a jedynie fragmenty obejmujące zmiany. Przed każdym fragmentem znajduje się nagłówek umieszczony między symbolami @@ - nagłówek ten informuje, od którego wiersza wyodrębniono zmiany i ile jest tych wierszy oraz, numer wiersza, od którego dodano zmiany i ile jest wierszy zmian.

Istnieje możliwość zastosowania szczegółowego wyróżniania zmian - wystarczy użyć polecenia git diff --color-words.

Porównywanie plików

Polecenia git diff można użyć również ograniczyć do konkretnego pliku. Do polecenia należy dopisać ścieżkę do pliku.

Porównywanie plików między commitami

Do polecenia git diff można również przekazać odniesienia do konkretnych commitów.

Aby pozyskać identyfikatory commitów można skorzystać z polecenia git log --pretty=oneline, gdzie dodatkowa flaga zapewnia lepszą czytelność.

git log --pretty=oneline

adbb92735b6b6b972831b6f0e7a998fe656f7d1f .
f70694fc55f6363de5a0e599099e32126efc3dd5 .
1140acd305c2451b2ad7ef9b503af455ec990554 .

Porównywanie gałęzi

Porównanie gałęzi odbywa się na takiej samej zasadzie jak w przypadku innych źródeł.

Schowek

W Git istnieje możliwość odłożenia wprowadzonych zmian do schowka.

Takie działanie może być szczególnie przydatne, gdy pojawi się konieczność zajęcia się inną częścią projektu, podczas gdy obecnie zmieniana jeszcze nie została dokończona. Pozwala to na szybką zmianę obszaru działania, ale przy zachowaniu niedokończonej pracy.

Dodawanie do schowka odbywa się za pomocą polecenia git stash. To polecenie pobiera niezatwierdzone zmiany (zapisane i niezapisane w przechowalni) i zapisuje je do użycia w przyszłości, jeśli zajdzie taka potrzeba.

git stash
PRZYKŁAD KODU

Domyślnie schowek oznaczany jest jako WIP (Work In Progress).

Po zastosowaniu tego polecenia możliwe jest rozpoczęcie pracy w innym miejscu - dodawanie nowych commitów, zmiana gałęzi. Istotnym jest, że schowek działa lokalnie - podczas wypychania zmian do repozytorium zdalnego zawarte w nim zmiany nie są przesyłane na serwer.

Zastosowanie zmian ze schowka

Aby zastosować zmiany zapamiętane w schowku, należy użyć polecenia got stash pop. Operacja pop powoduje usunięcie zmian ze schowka i zastosowanie ich do kopii roboczej. Pewną alternatywą jest zastosowanie polecenia git stash apply - umożliwia ono zastosowanie zmian do kopii roboczej i jednoczesne zachowanie ich w schowku. To polecenie może być przydatne, gdy zmiany ze schowka trzeba zastosować do wielu gałęzi.

Polecenie git stash domyślnie nie dodaje do schowka zmian dokonanych w plikach nieśledzonych oraz ignorowanych, co oznacza, że np. nowe w kopii roboczej pliki nie zostaną dodane do schowka.

Aby dodać do schowka pliki nieśledzone można skorzystać z opcji -u lub --include-untracked

Z kolei przekazanie do schowka zmian w plikach ignorowanych możliwe jest dzięki opcji -a lub --all

Wiele schowków

Wielokrotne zastosowanie polecenia git stash powoduje utworzenie wielu schowków.

Za pomocą polecenia git stash list wyświetlane są wszystkie schowki.

Schowkom nie nadaje się nazwy, ale można do nich dołączyć opis git stash save "opis"

W przypadku tworzenia wielu schowków polecenie git stash pop zostaną zastosowane zmiany z ostatniego utworzonego schowka, ale możliwe jest wskazanie schowka, z którego zmiany mają zostać ponownie zastosowane - odbywa się to przez dodanie identyfikatora schowka: git stash pop stash@{1}

Różnice między schowkami

Polecenie git stash show umożliwia wyświetlenie podsumowania schowka

Dodanie opcji -p lub --patch pokaże pełny zestaw różnic.

Częściowe dodawanie zmian do schowka

Git umożliwia dodawanie do schowka pojedynczych plików lub konkretnych zmian z plików.

Wykorzystanie opcji -p lub --patch spowoduje przejście przez każdy fragment zawierający zmiany - za każdym razem pojawi się pytanie, czy ma on zostać dodany do schowka.

Najczęściej stosowane polecenia:

  • y - dodaj ten fragment ze zmianami do schowka
  • n - nie dodawaj tego fragmentu ze zmianami do schowka
  • q - zakończ (wszystkie wybrane do tego momentu fragmenty ze zmianami zostaną dodane do schowka)
  • N - podziel fragment ze zmianami na mniejsze fragmenty
  • / - wyszukaj fragment ze zmianami za pomocą wyrażenia regularnego

Ignorowanie plików

Git wszystkie pliki widzi jako oznaczone jednym z trzech możliwych stanów:

  • śledzony - to taki plik, który został dodany do przechowalni (git add) lub zatwierdzony (git commit)
  • nieśledzony - plik, który nie został dodany do przechowalni ani zatwierdzony
  • ignorowany - plik, który ma być ignorowany na wyraźne polecenie

Najczęściej plikami ignorowanymi są te generowane maszynowo, pochodzące ze źródła repozytorium, powstające podczas kompilacji np.:

  • pamięci podręczne zależności (pliki znajdujące się w katalogach /packages)
  • skompilowany kod (.pyc, .class)
  • katalogi wyjściowe (/bin, /out)
  • pliki powstające podczas wykonywania (.log, .lock, .tmp)
  • ukryte pliki systemowe (.DS_Store)
  • pliki konfiguracji IDE (.idea/workspace.xml)

Pliki ignorowane git śledzi w ramach pliku .gitignore znajdującego się w katalogu głównym repozytorium.

W Git nie jest stosowane domyślne ignorowanie plików - jeżeli w repozytorium pojawią się nowe pliki, trzeba edytować plik .gitignore i zatwierdzić go.

W pliku .gitignore znajdują się określone wzorce, według których rozpoznawane są pliki przeznaczone do ignorowanie.

Wzorce ignorowania

W .gitignore można określić własne wzorce ignorowania plików korzystając z różnych symboli:

  • **/katalog - dopasowanie katalogu z dowolnej lokalizacji w repozytorium
  • *.log - dowolny plik z rozszerzeniem log
  • ? - zastępuje dokładnie jeden znak

Praca na gałęziach

Gałęzie to wskaźniki do migawek. Umożliwiają one pracę nad dowolną funkcją, naprawianie błędów w sposób hermetyczny, czyli w izolacji od głównej części kodu. Gałęzie umożliwiają równoległą pracę nad kilkoma funkcjami/elementami projektu i pozwalają zapobiec dodawaniu niepewnego kodu do głównej gałęzi.

Gałąź jest odwołaniem do commitu, ale prezentuje niezależną ścieżkę projektu.

Do tworzenia gałęzi służy polecenie git branch. Pozwala ono również na zmienianie nazw oraz usuwanie gałęzi. Należy pamiętać, że to polecenie nie pozwoli na zmianę gałęzi, ani scalenie ich.

Opcje polecenia git branch

  • --list - wyświetlenie wszystkich gałęzi
  • <branch> - tworzenie nowej gałęzi o podanej nazwie
  • -d <branch> - usunięcie konkretnej gałęzi (tzw. bezpieczne usuwanie - GIT nie pozwala na usuwanie gałęzi zawierającej niescalone zmiany)
  • -D <branch> - wymuszenie usunięcia gałęzi
  • -m <branch> - zmiana nazwy gałęzi
  • -a - wyświetlenie wszystkich zdalnych gałęzi

Tworzenie gałęzi

Tworzenie gałęzi odbywa się za pomocą polecenia git branch <branch>

Nowa gałąź jest tworzona na podstawie aktualnej gałęzi, czyli tej, na której aktualnie się znajdujemy.

Po utworzeniu gałęzi nadal znajdujemy się na gałęzi, z której została ona utworzona. Aby przełączyć się na nowo utworzoną gałąź, należy użyć polecenia git checkout <branch>.

Istnieje również możliwość utworzenia gałęzi i jednoczesnego przełączenia się na nią - odbywa się to za pomocą polecenia git checkout -b <branch>

Po utworzeniu gałęzi można na niej pracować, wprowadać zmiany, dodawać je do przechowalni i zatwierdzać korzystając ze znanych już poleceń git add i git commit. Zmiany wprowadzone na gałęzi nie będą miały wpływu na inne gałęzie, dopóki nie zostaną scalone.

Usuwanie gałęzi

Usuwanie gałęzi odbywa się za pomocą polecenia git branch -d <branch>

To polecenie jest bezpieczne, ponieważ nie pozwala na usunięcie gałęzi, która zawiera niescalone zmiany. Jeśli gałąź zawiera niescalone zmiany, można wymusić jej usunięcie za pomocą polecenia git branch -D <branch>

Usunięcie gałęzi nie powoduje usunięcia jej historii - nadal można ją znaleźć w historii projektu, ale nie będzie ona widoczna w standardowym widoku gałęzi.

Przełączanie między wersjami projektu

Przełączanie między wersjami projektu odbywa się za pomocą polecenia git checkout. Nazywane jest to wyewidencjonowaniem.

To polecenie pozwala na przełączanie się między gałęziami, ale również między konkretnymi commitami. Przełączanie się między gałęziami jest bezpieczne, ponieważ każda gałąź reprezentuje niezależną ścieżkę projektu, ale przełączanie się między commitami może być ryzykowne, ponieważ może prowadzić do utraty niezapisanych zmian.

Polecenie git checkout pozwala na przełączanie się między różnymi wersjami kodu, które znajdują się w lokalnej wersji repozytorium.

Sprawdzenie istniejących gałęzy umożliwia polecenie git branch

Polecenie git checkout -b <new> stworzy nową gałąź w miejscu bieżącego wskaźnika HEAD.

Zastosowanie polecenia git checkout <new> <existing> spowoduje utworzenie nowej gałęzi odchodzącej od już istniejącej.

Możliwe jest śledzenie historii wyewidencjonowania za pomocą polecenia git reflog

Detached HEAD

Detached HEAD to stan, w którym wskaźnik HEAD nie wskazuje na żadną gałąź, ale bezpośrednio na commit. Oznacza to, że jesteśmy w stanie przeglądać historię projektu i wprowadzać zmiany, ale nie możemy ich zatwierdzić ani wypchnąć do repozytorium zdalnego, ponieważ nie jesteśmy na żadnej gałęzi.

Stan Detached HEAD może być przydatny, gdy chcemy przeglądać historię projektu lub wprowadzić tymczasowe zmiany, ale nie chcemy ich zatwierdzać. Aby wyjść ze stanu Detached HEAD, należy przełączyć się na inną gałąź za pomocą polecenia git checkout <branch> lub utworzyć nową gałąź i przełączyć się na nią za pomocą polecenia git checkout -b <new>

Scalanie zmian

Scalanie zmian odbywa się za pomocą polecenia git merge. To polecenie pozwala na połączenie dwóch gałęzi, co oznacza, że zmiany wprowadzone na jednej gałęzi zostaną przeniesione na drugą gałąź.

Scalanie jest bezpieczne, ponieważ Git automatycznie wykrywa konflikty i pozwala na ich rozwiązanie przed zatwierdzeniem zmian.

Istnieje również możliwość zastosowania polecenia git rebase do scalania zmian, ale jest to bardziej zaawansowana operacja, która może prowadzić do utraty historii projektu, jeśli nie jest używana ostrożnie.

Przed scaleniem

Przed scaleniem warto sprawdzić, czy wskaźnik HEAD wskazuje na odpowiednią gałąź odbiorczą. Można w tym celu użyć polecenia git status, które pokaże aktualną gałąź, na której się znajdujemy. Należy również upewnić się, że wszystkie zmiany zostały zatwierdzone lub odłożone do schowka, aby uniknąć utraty pracy podczas scalania.

Scalanie z przewijaniem

Scalanie z przewijaniem (fast-forward) to sytuacja, w której gałąź docelowa jest bezpośrednio przed gałęzią źródłową, co oznacza, że nie ma żadnych dodatkowych commitów między nimi. W takim przypadku Git po prostu przesuwa wskaźnik gałęzi docelowej do gałęzi źródłowej, co jest szybkie i proste.

#Start a new feature
git checkout -b new-feature main
#Edit some files
git add <file>
git commit -m "Start a feature"
#Edit some files
git add <file>
git commit -m "Finish a feature"
#Merge in the new-feature branch
git checkout main
git merge new-feature
git branch -d new-feature

Stosowane na końcu polecenie git branch -d nie powinno zwrócić błędów ze względu na to, że nowa funkcja została już scalona z główną gałęzią.

Scalanie z przewijaniem domyślnie nie tworzy commitu, ale możliwe jest wymuszenie wygenerowania commitu scalenia - odbywa się to za pomocą opcji --no-ff (no fast-forward)

Scalanie trójstronne

Scalanie trójstronne to sytuacja, w której gałąź docelowa i gałąź źródłowa mają wspólnego przodka, ale istnieją dodatkowe commity między nimi. W takim przypadku Git tworzy nowy commit scalający, który łączy zmiany z obu gałęzi i zawiera informacje o tym, które zmiany zostały wprowadzone na każdej z gałęzi.

#Start a new feature
git checkout -b new-feature main
#Edit some files
git add <file>
git commit -m "Start a feature"
#Edit some files
git add <file>
git commit -m "Finish a feature"
#Develop the main branch
git checkout main
#Edit some files
git add <file>
git commit -m "Make some super-stable changes to main"
#Merge in the new-feature branch
git merge new-feature
git branch -d new-feature

W powyższym przypadku prace na gałęzi main prowadzone są jednoczeście z pracami na nowej gałęzi.

Warto zwrócić uwagę, że zanim zostanie wykonane polecenie git merge należy przełączyć się na docelową gałąź (w tym przypadku main) za pomocą polecenia git checkout.

Konflikty

Konflikty podczas scalania występują, gdy Git nie jest w stanie automatycznie połączyć zmian z obu gałęzi. Dzieje się tak, gdy te same linie kodu zostały zmienione w obu gałęziach, a Git nie wie, które zmiany powinny zostać zachowane. Konflikt scalania może również wystąpić na etapie uruchamiania scalania - jeżeli w katalogu roboczym lub przechowalni projektu znajdują się oczekujące zmiany. Wtedy GIT nie może przeprowadzić scalania, ponieważ te zmiany mogłyby zostać nadpisane scalanymi commitami.

Podczas scalania, jeśli wystąpi konflikt, Git oznaczy pliki z konfliktem i poprosi o ręczne rozwiązanie konfliktu. Pliki z konfliktem będą zawierały specjalne znaczniki, które wskazują, które zmiany pochodzą z której gałęzi. Po rozwiązaniu konfliktu, należy dodać zmienione pliki do przechowalni i zatwierdzić zmiany, aby zakończyć proces scalania.

GIT stosuje wizualne oznaczenia do sprzecznej zawartości scalanych elementów.

  • <<<<<<<
  • =======
  • >>>>>>>

To co znajduje się po lewej stronie znacznika pochodzi z gałęzi odbiorczej, po prawej z gałęzi scalanej.

Po znalezieniu miejsc z konfliktami można do nich przejść i je naprawić. Po dokonaniu zmian należy użyć polecenia git add na każdym z naprawionych plików, a następnie zatwierdzić zmiany poleceniem git commit, aby zakończyć proces scalania.

Konflikty scalania występują wyłącznie w przypadku scalania trójstronnego.

Identyfikowanie przyczyn konfliktów

Poniżej przedstawiono symulację sytuacji zaistnienia konfliktu scalania.

mkdir new-repo
cd new-repo
git init .
echo "some changes" > merge-test.txt
git add merge-test.txt
git commit -am"initial commit"

Przedstawiony kod tworzy nowe repozytorium, dodaje do niego plik i zatwierdza zmiany.

git checkout -b branch_to_merge
echo "new content" > merge-test.txt
git commit -am"edited"

W powyższym kodzie stworzona została nowa gałąź, wprowadzono tekst do pliku merge-test.txt i zatwierdzono je. 

git checkout main
echo "new content to append" >> merge-test.txt
git commit -am"append new content"

W tym przypadku następuje przełączenie na gałąź main oraz dodanie nowej treści do pliku oraz zatwierdzenie wprowadzonych zmian.

Zastosowanie polecenia git merge branch_to_merge spowoduje wystąpienie konfliktu scalania - zarówno w gałęzi main, jak i branch_to_merge istnieją nowe commity.

W celu zidentyfikowania przyczyn konfliktów można skorzystać z polecenia git log --merge, które pokaże historię commitów będących częścią procesu scalania i mogą być przyczyną konfliktów.

Można również zastosować polecenie git status.

Zastosowanie polecenia cat merge-test.txt wyświetla zawartość pliku merge-test.txt z wizualnymi oznaczeniami konfliktu.

Konflikt można rozwiązać poprzez zmodyfikowanie pliku będącego źródłem konfliktu. Po wprowadzeniu zmian należy dodać zmienione pliki do przechowalni i zatwierdzić zmiany, aby zakończyć proces scalania.

Możliwe jest również zastosowanie polecenia git merge --abort by zakończyć scalanie i przywrócić gałąź do stanu sprzed rozpoczęcia scalania.

Tagowanie

Tagowanie to proces przypisywania etykiet do konkretnych commitów w historii projektu. Tag jest wskaźnikiem do konkretnego commitu i służy do oznaczania ważnych punktów w historii projektu, takich jak wydania, wersje lub inne istotne momenty. Tagowanie pozwala na łatwe odnalezienie i identyfikację tych punktów w historii projektu. Tagowanie jest szczególnie przydatne w przypadku zarządzania wersjami oprogramowania, gdzie ważne jest oznaczanie konkretnych wersji, które zostały wydane lub są gotowe do wydania.

Utworzenie nowego tagu wymaga użycia polecenia git tag <nazwa_tagu>. Popularnym rozwiązaniem jest używanie numerów wersji np v1.1

Typy tagów

GIT obsługuje dwa typy tagów.

Tagi adnotowane

Przechowywane są jako obiekty w bazie danych GIT. Zawierają metadane związane z twórcą oraz datą utworzenia. Tagi adnotowane są podpisywane cyfrowo, co zapewnia ich autentyczność i integralność. Tagi adnotowane są bardziej trwałe i bezpieczne niż tagi lekkie, ponieważ zawierają dodatkowe informacje i są podpisywane cyfrowo.

Utworzenie tagu adnotowanego odbywa się za pomocą polecenia git tag -a <nazwa_tagu> -m "opis"

Tagi lekkie

Nie są przechowywane jako obiekty w bazie danych GIT, ale są po prostu wskaźnikami do konkretnego commitu. Tagi lekkie nie zawierają dodatkowych informacji, takich jak metadane czy podpisy cyfrowe, co sprawia, że są mniej trwałe i bezpieczne niż tagi adnotowane. Tagi lekkie są bardziej podatne na przypadkowe usunięcie lub modyfikację, ponieważ nie zawierają dodatkowych informacji i nie są podpisywane cyfrowo.

Utworzenie tagu lekkiego odbywa się za pomocą polecenia git tag <nazwa_tagu> bez dodatkowych opcji.

Tagi można również tworzyć na podstawie istniejących tagów, gałęzi lub commitów, poprzez dodanie do polecenia git tag odpowiedniego odniesienia, np. git tag <nazwa_tagu> <odniesienie>, gdzie <odniesienie> może być nazwą istniejącego tagu, gałęzi lub identyfikatorem commitu.

Wyświetlanie listy tagów

Wyświetlenie listy wszystkich tagów w repozytorium odbywa się za pomocą polecenia git tag.

Dodanie opcji -l pozwala uszczegółowić wyświetlaną listę.

Możliwe jest również wyświetlenie szczegółowych informacji o konkretnym tagu, w tym jego typu, autora, daty utworzenia i opisu, za pomocą polecenia git show <nazwa_tagu>.

Tagowanie wybranych commitów

Domyślnie polecenie git tag tworzy tag na commicie, przy którym znajduje się wskaźnik HEAD. Możliwe jest jednak stworzenie tagu do starszych commitów.

W tym celu należy dodać do polecenia git tag identyfikator commitu, do którego ma zostać przypisany tag, np. git tag <nazwa_tagu> <identyfikator_commitu>

Listę commitów uzyskuje się przy pomocy polecenia git log --pretty=oneline.

Operacje na tagach

Usunięcie tagu odbywa się za pomocą polecenia git tag -d <nazwa_tagu>.

Zmiana nazwy tagu odbywa się za pomocą polecenia git tag -m <stara_nazwa> <nazwa_tagu>.

Ponowne tagowanie lub zastępowanie starszych tagów można wykonać za pomocą polecenia git tag -a -f z identyfikatorem właściwego commitu (-f oznacza FORCE).

Cofanie zmian

Cofanie zmian w GIT to proces przywracania wcześniejszego stanu projektu poprzez usuwanie lub modyfikowanie commitów. GIT oferuje różne narzędzia do cofania zmian, takie jak git reset, git revert i git checkout.

Każde z tych narzędzi ma swoje zastosowanie i różni się sposobem działania oraz wpływem na historię projektu. Wybór odpowiedniego narzędzia do cofania zmian zależy od konkretnej sytuacji i potrzeb projektu.

git reset

Polecenie git reset służy do cofania zmian poprzez przesuwanie wskaźnika HEAD do wcześniejszego commitu. To polecenie może być używane do usuwania commitów z historii projektu, ale należy zachować ostrożność, ponieważ może prowadzić do utraty danych, jeśli nie jest używane prawidłowo.

Istnieją trzy główne tryby działania polecenia git reset:

  • --soft - przesuwa wskaźnik HEAD do wcześniejszego commitu, ale pozostawia zmiany wprowadzone w commitach jako niezatwierdzone (staged)
  • --mixed - przesuwa wskaźnik HEAD do wcześniejszego commitu i pozostawia zmiany wprowadzone w commitach jako niezatwierdzone (unstaged)
  • --hard - przesuwa wskaźnik HEAD do wcześniejszego commitu i usuwa wszystkie zmiany wprowadzone w commitach, przywracając stan projektu do tego commitu

Użycie polecenia git reset z opcją --hard jest nieodwracalne, ponieważ usuwa wszystkie zmiany wprowadzone w commitach, dlatego należy używać go z dużą ostrożnością.

git revert

Polecenie git revert służy do cofania zmian poprzez tworzenie nowego commitu, który odwraca zmiany wprowadzone przez wcześniejszy commit. To polecenie jest bezpieczne, ponieważ nie usuwa żadnych commitów z historii projektu, ale dodaje nowy commit, który odwraca zmiany wprowadzone przez wcześniejszy commit.

Użycie polecenia git revert jest szczególnie przydatne, gdy chcemy cofnąć zmiany wprowadzone przez wcześniejszy commit, ale nie chcemy usuwać żadnych commitów z historii projektu. Polecenie to jest również przydatne, gdy chcemy cofnąć zmiany wprowadzone przez commit, który został już wypchnięty do repozytorium zdalnego, ponieważ nie powoduje to konfliktów z innymi commitami w historii projektu.

git checkout

Polecenie git checkout służy do cofania zmian poprzez przełączanie się na wcześniejszy commit lub gałąź. To polecenie pozwala na przeglądanie historii projektu i wprowadzanie zmian, ale nie jest zalecane do cofania zmian, ponieważ może prowadzić do utraty danych, jeśli nie jest używane prawidłowo.

Użycie polecenia git checkout do cofania zmian jest szczególnie ryzykowne, ponieważ może prowadzić do utraty niezapisanych zmian, jeśli nie zostaną one zatwierdzone lub odłożone do schowka przed przełączeniem się na wcześniejszy commit lub gałąź. Dlatego zaleca się używanie tego polecenia tylko do przeglądania historii projektu i wprowadzania zmian, a nie do cofania zmian.

Polecenie git clean

Polecenie git clean służy do usuwania nieśledzonych plików z katalogu roboczego. To polecenie jest przydatne, gdy chcemy usunąć pliki, które nie są śledzone przez GIT, ale należy zachować ostrożność, ponieważ może prowadzić do utraty danych, jeśli nie jest używane prawidłowo.

Użycie polecenia git clean z opcją -f (force) jest nieodwracalne, ponieważ usuwa wszystkie nieśledzone pliki z katalogu roboczego, dlatego należy używać go z dużą ostrożnością.

Polecenie git rm

Polecenie git rm służy do usuwania plików z katalogu roboczego i z indeksu GIT. To polecenie usuwa plik z systemu plików i z indeksu GIT, co powoduje, że plik nie będzie już śledzony przez GIT. W przypadku usunięcia pliku z katalogu roboczego bez użycia tego polecenia, GIT nie będzie wiedział, że plik został usunięty.

Zdalne repozytoria

Zdalne repozytoria to kopie lokalnych repozytoriów, które są przechowywane na serwerze lub w chmurze. Służą do współpracy nad projektem z innymi osobami, umożliwiając im dostęp do kodu i historii projektu. Zdalne repozytoria pozwalają na synchronizację zmian między różnymi lokalnymi repozytoriami, co ułatwia współpracę nad projektem.

GIT obsługuje różne platformy do hostowania zdalnych repozytoriów, takie jak GitHub, GitLab, Bitbucket i inne. Każda z tych platform oferuje różne funkcje i możliwości, ale wszystkie umożliwiają zarządzanie zdalnymi repozytoriami i współpracę nad projektami.

Podstawowe operacje związane ze zdalnymi repozytoriami obejmują dodawanie zdalnych repozytoriów, pobieranie zmian z zdalnych repozytoriów, wypychanie zmian do zdalnych repozytoriów, zarządzanie gałęziami zdalnymi i rozwiązywanie konfliktów zdalnych.

Tworzenie połączeń ze zdalnymi repozytoriami

Dodanie zdalnego repozytorium odbywa się za pomocą polecenia git remote add <nazwa> <url>, gdzie <nazwa> to nazwa, którą chcemy przypisać do zdalnego repozytorium, a <url> to adres URL zdalnego repozytorium.

Po dodaniu zdalnego repozytorium, można używać jego nazwy do wykonywania operacji związanych ze zdalnymi repozytoriami, takich jak pobieranie zmian, wypychanie zmian i zarządzanie gałęziami zdalnymi.

Adresy repozytoriów zdalnych

Adresy repozytoriów zdalnych mogą być w różnych formatach, w zależności od protokołu używanego do komunikacji z serwerem. Najczęściej spotykane formaty adresów repozytoriów zdalnych to:

  • https ://github.com/user/repo.git - adres URL dla protokołu HTTPS
  • git ssh:user@host/path/to/repo.git - adres URL dla protokołu SSH

Ściąganie i wypychanie

Ściąganie zmian z zdalnego repozytorium odbywa się za pomocą polecenia git pull <remote> <branch>, gdzie <remote> to nazwa zdalnego repozytorium, a <branch> to nazwa gałęzi, z której chcemy pobrać zmiany.

Wypychanie zmian do zdalnego repozytorium odbywa się za pomocą polecenia git push <remote> <branch>, gdzie <remote> to nazwa zdalnego repozytorium, a <branch> to nazwa gałęzi, do której chcemy wypchnąć zmiany.

Problemy

Podczas pracy z git mogą pojawić się różne problemy, które mogą być związane z konfliktem zmian, błędami podczas łączenia gałęzi, problemami z repozytorium zdalnym, błędami podczas wypychania zmian do repozytorium zdalnego, problemami z autoryzacją, problemami z konfiguracją, problemami z narzędziami do zarządzania repozytoriami, problemami z siecią.
